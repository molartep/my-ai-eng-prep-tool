# fundamentals
Large language models|An LLM learns a distribution over token sequences, enabling conditional text generation rather than database lookup.|Training adjusts parameters to predict text; inference conditions each next-token distribution on the prompt and prior output.|Fluent continuation is useful for language tasks but does not establish factual truth.|A support model confidently invents an undocumented refund policy. What changes would you make?|Retrieve authoritative policy, require citations, test abstention, and route unsupported cases to a person rather than relying on confident wording.|Every output is a retrieved training document~Fluency proves factual accuracy~A larger model always eliminates hallucinations
Tokens and tokenization|Tokens are vocabulary units such as subwords, punctuation, or bytes; they are not necessarily words.|A tokenizer maps text to IDs and the model predicts IDs that are decoded back to text.|Language and code can have different token densities, affecting both context limits and latency.|English and Japanese versions of the same article have different token counts. How should you budget context?|Measure with the actual tokenizer, reserve output capacity, and truncate by semantic boundaries rather than counting words.|One token always equals one word~All models use the same tokenizer~Character count exactly predicts token count
Transformer attention|Attention forms contextual representations by weighting value vectors according to query-key compatibility.|Scaled dot-product attention computes softmax(QK transpose / sqrt(d))V; causal masks prevent attending to future tokens during autoregressive training.|Dense attention mixes information effectively but its pairwise interactions grow quadratically with sequence length.|A longer prompt causes memory pressure before generation starts. Why, and what can help?|Separate prefill from decode, inspect attention and KV-cache memory, shorten or retrieve context, and consider efficient attention implementations.|Attention weights are calibrated confidence scores~Causal models see future tokens at inference~Longer prompts have no memory cost
Context windows|The context window bounds the tokens a model can consider in a single request, including the applicable input and output budget.|The runtime formats instructions, history, evidence, tool results, and generated tokens inside model-specific limits.|Fitting information into the window does not ensure the model will use it correctly.|A chat forgets an early constraint after many tool calls. How would you handle context?|Persist canonical task state separately, compact redundant observations, preserve constraints, and evaluate summary fidelity.|Context is unlimited persistent memory~Anything inside the window is always used~Summarization cannot lose constraints
Sampling controls|Temperature rescales logits; top-p retains a probability-mass nucleus and top-k restricts the candidate count.|Sample from a transformed token distribution or use greedy decoding to select a high-probability continuation.|Lower temperature can reduce variation but does not guarantee correctness or repeatability across runtimes.|A classifier changes labels between runs despite temperature zero. What should you investigate?|Check model and prompt versions, numerical nondeterminism, ambiguous inputs, and constrain outputs; measure agreement across repeated runs.|Temperature zero guarantees truth~Top-p changes the context length~High temperature guarantees creativity without errors
Embeddings and cosine similarity|An embedding is a learned vector representation; cosine similarity measures angle rather than vector magnitude.|For vectors u and v, cosine equals dot(u,v)/(norm(u)norm(v)); compatible encoders put related inputs near each other.|Similarity reflects the encoder's training objective and may miss negation, numeric differences, or domain terms.|The query about permitted actions retrieves a policy saying actions are prohibited. Why?|Test negation and domain examples, add lexical signals or a reranker, and verify evidence rather than treating proximity as entailment.|Similarity proves entailment~Embeddings from any model are interchangeable~Cosine depends only on vector magnitude
Structured outputs|Structured generation constrains a response to a declared schema, while application validation checks business meaning.|Declare required properties and types, handle refusal or truncation, parse output, then validate cross-field invariants.|Syntactic schema compliance does not ensure factual accuracy or authorized actions.|A valid JSON order contains a negative quantity. How do you fix the pipeline?|Use bounded numeric fields where supported and enforce inventory, authorization, and cross-field rules in application code.|Valid JSON proves business validity~A schema authorizes side effects~Refusals never need handling
RAG versus fine-tuning|RAG supplies selected information at inference; fine-tuning changes parameters to improve learned behavior.|Retrieve updated documents for evidence; train on examples when format, style, or recurring task behavior needs adaptation.|Fine-tuning is not a reliable substitute for rapidly changing, attributable knowledge.|Policies change weekly but the model must use a consistent response style. Which approach fits?|Use RAG for fresh policy and consider fine-tuning only after prompting and evaluations show a behavioral gap; the two can coexist.|Fine-tuning guarantees current knowledge~RAG changes model weights~The methods cannot be combined
Quantization and model selection|Quantization represents model values at lower precision to reduce storage and memory, sometimes improving serving efficiency.|Load quantized weights supported by the runtime, then benchmark task accuracy, context memory, and throughput on the target hardware.|Lower precision may degrade sensitive tasks; weight size alone omits KV-cache and runtime overhead.|A 4-bit model fits in RAM but becomes slow on long interviews. What do you measure?|Measure prefill, tokens per second, swap pressure, KV-cache growth, and task quality; compare smaller models and shorter context.|4-bit weights remove KV-cache memory~Quantization never changes quality~Parameter count alone predicts latency
# failures
Hallucinations|Hallucination is generated content that is unsupported or false under the task's grounding requirements.|Next-token plausibility can favor familiar patterns even when evidence is absent, conflicting, or misunderstood.|Grounding and abstention reduce risk but are not proofs of truth.|A model supplies a plausible citation to a nonexistent paper. How would you prevent this?|Validate citation identifiers against retrieved records, show evidence spans, and test unsupported queries with explicit abstention.|A fluent citation must exist~RAG prevents every hallucination~Confidence language is calibrated probability
Lost in the middle|Evidence position within a long prompt can affect whether a model uses it successfully.|Models may underutilize central context compared with early or late evidence; the effect depends on task and model.|Large advertised windows do not guarantee uniform information use.|The answer is present halfway through a large prompt, but the model misses it. What experiments isolate the issue?|Hold content fixed and vary position, reduce distractors, rerank evidence, and separate retrieval coverage from generation use.|Window capacity guarantees effective use~Missing answers always mean retrieval failed~Evidence order never matters
Prompt injection|Prompt injection occurs when untrusted text attempts to redirect model behavior across a trust boundary.|An attacker places commands in retrieved content or tool output; the model may treat those commands as instructions.|Prompt wording alone cannot enforce security against all adversarial inputs.|A retrieved document tells the assistant to export customer records. What controls belong outside the model?|Enforce least-privilege tools, application authorization, data isolation, egress limits, and approvals bound to exact operations.|Retrieved text has system authority~A warning prompt is a complete security boundary~Tool authorization belongs to the model
Knowledge freshness|Parametric knowledge reflects training and adaptation history, not a live view of changing facts.|Provide timestamped current records through controlled retrieval and reconcile conflicting versions.|Recent-sounding language is not evidence of a recent source.|The model cites last year's pricing while retrieval returns current pricing. What would you inspect?|Trace the selected evidence and prompt, prioritize authoritative dated records, and test whether the generated claim is supported.|The model always knows today's facts~Training date guarantees coverage~Source recency can be inferred from tone
Context contamination|Irrelevant or stale information in a prompt can bias later reasoning and generation.|Earlier mistaken assumptions, old tool outputs, and unrelated conversations compete with current task evidence.|More context can decrease quality when relevance and provenance are uncontrolled.|An agent repeats an obsolete address from earlier conversation. What changes help?|Keep verified state with versioned fields, invalidate stale observations, and distinguish user statements from confirmed records.|More history always improves accuracy~All tool outputs stay fresh~A model corrects stale state automatically
Tool selection errors|A tool selection error is choosing an inappropriate operation or failing to request a needed operation.|Ambiguous descriptions, overlapping tools, and incomplete task state can lead to incorrect requests.|A correct tool name does not imply valid arguments, successful execution, or safe side effects.|A read-only support request triggers a delete operation. How would you debug and contain it?|Trace the tool-selection decision, narrow exposed tools, make descriptions distinct, and enforce read-only permissions at execution.|Correct arguments justify any operation~Tool exposure implies authorization~Models never confuse similar tools
Structured output failures|Responses can be malformed, truncated, refused, or syntactically valid but semantically wrong.|The parser and schema validator must distinguish transport failure, incomplete generation, and domain validation failures.|Blind retries can duplicate effects or produce endless repair loops.|An extraction model emits half a JSON object. What should happen?|Treat truncation as failure, retain raw diagnostic output safely, cap repair attempts, and avoid downstream writes until validation succeeds.|Parsing success guarantees truth~Any invalid output should be executed partially~Unlimited retries are harmless
Compounding agent failures|Multi-step execution can amplify small local mistakes through dependent actions.|If n independent required steps each succeed with probability p, total success is p to the n; real errors are often correlated.|For p=0.95 and n=10, success is about 0.599, but independence is a simplifying assumption.|A ten-step agent fails far more often than its single-step benchmark predicts. What should you measure?|Inspect whole trajectories, dependencies and correlated failures; add verification at critical boundaries and simplify unnecessary steps.|95% step accuracy implies 95% task success~Failures are always independent~Adding agents necessarily improves reliability
Grounding and abstention|Grounding ties claims to available evidence; abstention declines to answer when support is insufficient.|Retrieve relevant facts, generate constrained claims, verify support, and communicate uncertainty or request clarification.|An answer can faithfully repeat an incorrect source, so grounding differs from real-world correctness.|A cited policy is outdated but every sentence is supported by it. Which quality dimension failed?|Faithfulness may pass; correctness and freshness fail. Check authority, version, and task-date requirements independently.|Grounded answers are always true~Abstention is always a failure~Citations alone establish support
# rag
RAG architecture|RAG combines information retrieval with generation so answers can use external evidence.|Offline ingestion parses, chunks, embeds and indexes; online query processing retrieves, reranks, assembles context and generates cited answers.|Retrieval, evidence use, freshness, and permissions must each be evaluated independently.|A document QA system returns wrong answers after a policy update. How do you isolate the cause?|Check ingestion version, indexing completion, retrieved evidence, context assembly, and final claim support stage by stage.|RAG always trains model weights~Retrieval success guarantees answer correctness~The index never needs updating
Document ingestion and parsing|Ingestion converts source documents into searchable records while preserving structure and provenance.|Extract text, tables and headings; normalize carefully; store document IDs, versions, access metadata and source offsets.|Poor parsing can destroy semantics before retrieval begins.|Invoices lose table headers during PDF extraction. What change would you prioritize?|Inspect parsed samples, retain row-column associations and page provenance, then evaluate downstream retrieval before tuning embeddings.|Embedding models reconstruct missing table headers~Parsing quality is irrelevant~All file formats extract identically
Chunk size and overlap|Chunking divides documents into retrieval units, balancing specificity with sufficient explanatory context.|Split at meaningful boundaries, retain headings, and use bounded overlap to preserve cross-boundary meaning.|Tiny chunks lose context; large chunks dilute relevance; overlap can duplicate evidence.|A policy exception lies just after a chunk boundary and is missed. What would you test?|Compare semantic boundaries, overlap, and parent expansion on labeled queries; check citation offsets and deduplicate results.|One universal chunk size fits all corpora~More overlap is always better~Chunk boundaries cannot change answer quality
Vector search and ANN|Vector search ranks encoded items by similarity; approximate nearest neighbor indexes trade exactness for speed.|Index compatible vectors and search a candidate region; tune index parameters against exact-search recall and latency.|Approximation can miss good neighbors and must be separated from semantic relevance errors.|Exact vector search finds a document that ANN misses. What does that indicate?|Measure ANN recall against exact neighbors, tune search effort and index settings, and avoid blaming the embedding model prematurely.|ANN always returns exact nearest neighbors~Vector proximity proves relevance~Index tuning changes the model's semantics
BM25 and hybrid retrieval|BM25 scores lexical matches with term-frequency saturation and length normalization; hybrid retrieval combines lexical and semantic candidates.|Run sparse and dense retrieval, then merge using calibrated scores or rank fusion such as RRF.|Dense similarity and lexical scores are not directly comparable without normalization or rank-based fusion.|A query for error code ZX-401 retrieves vaguely similar documents. What retrieval change fits?|Add lexical retrieval for exact identifiers, fuse rankings, and evaluate identifier-heavy queries as a distinct slice.|Dense search always handles exact IDs best~Raw scores from different retrievers have equal meaning~BM25 uses learned dense embeddings
Metadata filtering and permissions|Metadata filtering limits retrieval to records satisfying conditions such as tenant, date, or document type.|Apply access constraints before evidence reaches the model and propagate permissions through ingestion and caches.|Post-generation filtering is too late to prevent confidential context exposure.|A cross-tenant document appears in a support answer. Where should enforcement occur?|Enforce tenant authorization in retrieval and cache keys, test adversarial queries, and audit document metadata propagation.|Removing secret text after generation is sufficient~Similarity scores encode authorization~Shared cache keys are safe across tenants
Query rewriting and multi-query retrieval|Query transformation makes user intent more searchable; multiple rewrites broaden candidate coverage.|Resolve references using conversation state, generate alternate formulations, retrieve, merge, and deduplicate evidence.|Rewrites can drift from intent, multiply latency, and drop exact constraints.|A rewrite removes the user's date restriction. How would you detect and mitigate drift?|Preserve structured constraints separately, compare original-query results, and evaluate rewrites on constraint-sensitive cases.|Rewrites always preserve meaning~More queries always reduce latency~Query constraints belong only in generated prose
Reranking and cross-encoders|A reranker rescores candidate query-document pairs to improve ordering before context assembly.|A cross-encoder jointly processes query and candidate text, unlike independent embeddings, so it can model richer interactions.|It cannot recover relevant documents missing from the candidate set and adds inference cost.|Top-50 retrieval contains the right passage but top-5 context does not. What would you investigate?|Measure candidate recall and reranker ordering, check truncation, and compare reranker latency-quality trade-offs.|Reranking guarantees full corpus recall~A reranker generates the answer~Independent embeddings are cross-encoder scoring
Parent-child retrieval and context assembly|Parent-child retrieval searches specific child chunks and expands selected hits into richer parent context.|Map child IDs to parents, deduplicate overlapping expansions, and assemble evidence within a token budget with provenance.|Expansion can introduce distractors or overwhelm the prompt if parents are too large.|Short search hits rank well but omit surrounding qualifications. What design helps?|Retrieve precise children, expand relevant parents with bounded windows, preserve evidence IDs, and evaluate claim support after assembly.|Parent expansion has no token cost~Every parent must be included in full~Context assembly order cannot affect results
# rag-evaluation
Precision@K and Recall@K|Precision@K is relevant retrieved items divided by K; Recall@K is relevant retrieved items divided by all known relevant items.|With K=5, two relevant hits and four relevant corpus items, precision=2/5=0.4 and recall=2/4=0.5.|Recall requires sufficiently complete relevance judgments; both metrics ignore ordering within the first K.|Increasing K improves recall but adds distracting context. How would you decide the cutoff?|Plot precision-recall-latency and answer quality over K; choose for task needs rather than maximizing recall alone.|Precision and recall use the same denominator~Precision measures evidence position~Recall can exceed one
Hit Rate@K|Hit Rate@K is the fraction of queries with at least one relevant result in the first K positions.|For hit indicators [1,0,1,1], average hit rate is 3/4=0.75.|One relevant result can count as success even when a multi-hop answer needs several facts.|A retriever has 95% hit rate but misses half the facts needed for comparisons. Why?|Hit rate tests at least one hit, so add recall and evidence coverage per required fact; inspect multi-document queries separately.|Hit rate counts all relevant documents~High hit rate guarantees multi-hop completeness~Hit rate is the reciprocal of rank
Mean Reciprocal Rank|MRR averages the reciprocal rank of the first relevant result, using zero when none appears within the evaluation cutoff.|First relevant ranks 1,2,none give (1+0.5+0)/3=0.5.|MRR values early first hits but ignores additional relevant results.|Two systems have the same MRR but different evidence coverage. How can that happen?|Their first useful results occur at similar ranks while later relevant items differ; measure recall or MAP alongside MRR.|MRR averages every relevant rank~Missing hits are excluded from the denominator~MRR measures factual answer correctness
Mean Average Precision|Average Precision averages precision at relevant ranks, normally divided by the total number of relevant items; MAP averages AP over queries.|For relevant ranks 1 and 3 with two relevant items, AP=(1/1+2/3)/2=0.833.|State the cutoff and denominator convention; incomplete labels distort both ordering and coverage estimates.|A benchmark uses AP@5 divided by min(R,5). Why must reports disclose this?|Truncated AP conventions differ; two reported MAP scores may not be comparable without identical relevance labels and denominator rules.|AP and MRR are identical~AP ignores later relevant documents~Cutoff conventions never affect comparisons
NDCG|NDCG measures ranked graded relevance normalized by the best possible ordering.|Using gain 2^rel-1, DCG@K sums gain/log2(rank+1); divide by IDCG. Labels [0,3] yield 4.416/7=0.631.|Labels, gain functions and cutoff affect interpretation; define behavior when ideal gain is zero.|A system retrieves all relevant passages but puts weak evidence first. Which metric helps?|Use graded NDCG to value ordering, keep recall for coverage, and report per-query deltas rather than only aggregate improvements.|NDCG ignores rank~NDCG has no relevance labels~A zero ideal gain can be divided normally
Context precision and context recall|Context precision estimates useful retrieved context; context recall estimates how much required answer evidence the context covers.|Annotate useful chunks or claims and compute a declared proportion; implementations may rank-weight useful chunks or use judge-based claim coverage.|These names have multiple implementations, so specify unit, judgment method and denominator.|Two tools report different context precision for identical retrieval. What should you compare?|Check whether they score chunks, tokens or claims, rank weighting, judges, labels and treatment of duplicates.|Metric names guarantee identical formulas~Reference-free recall needs no assumptions~All retrieved tokens are equally useful
Faithfulness and groundedness|Faithfulness measures whether answer claims are supported by supplied context rather than unsupported additions.|Decompose an answer into verifiable claims; check entailment from evidence; report supported claims divided by evaluable claims.|Faithfulness does not establish correctness of the source or completeness of the answer.|Retrieval recall is high but the answer adds a nonexistent exception. What failed?|Inspect generation prompts, conflicting evidence and claim-level support; compare oracle context before changing retrieval.|Faithfulness measures retrieval recall~A faithful answer must be complete~Citing a document proves every claim
Answer relevancy and correctness|Relevancy measures whether an answer addresses the request; correctness measures whether its substantive claims match task truth.|Use explicit rubrics or references, check required facts, and score scope, accuracy and unsupported additions separately.|Semantic similarity can overrate answers that share wording but reverse a number or negation.|An answer repeats the right vocabulary but says a limit is 500 instead of 50. What evaluation catches this?|Use numeric fact checks and correctness judgments against authoritative evidence; do not rely on embedding similarity alone.|Similar wording guarantees correct numbers~Relevancy proves truth~Correctness and faithfulness are always identical
Diagnosing retrieval versus generation|Stage-specific evaluation separates evidence availability from the generator's ability to use evidence.|Measure labeled candidate recall, reranked coverage, assembled context and answer claims; run generation with oracle context as an intervention.|End-to-end scores alone hide causes, and oracle experiments must keep the prompt and model controlled.|Answer quality stays poor even with manually selected perfect evidence. What do you investigate next?|Inspect instructions, evidence placement, contradictory history, output constraints and model capability; retrieval tuning alone will not resolve the generation defect.|Every wrong answer is a retrieval error~End-to-end averages explain root cause~Oracle context changes must include a new model
# agents
Agent versus workflow|A workflow follows predefined orchestration while an agent lets a model choose some actions based on goals and observations.|Production systems often embed a bounded model-driven decision loop within deterministic routing and validation.|Autonomy helps with variable tasks but increases uncertainty, cost and evaluation complexity.|A predictable three-step task has been replaced by an agent and becomes unreliable. What would you change?|Restore deterministic steps where requirements are fixed and reserve model decisions for genuine ambiguity; evaluate whole-task success.|All LLM applications are autonomous agents~Workflows cannot contain models~Autonomy always improves reliability
Agent loop|An agent loop repeatedly decides, requests actions, observes results, updates state and decides whether to stop.|The runtime sends state and allowed tools to the model, validates and executes requests, appends observations, and applies termination checks.|Each iteration consumes latency and tokens; tool success and goal completion require explicit verification.|An agent repeats the same unsuccessful search indefinitely. How would you stop and recover it?|Cap steps, wall time and tokens; detect repeated state-action pairs; classify the failure and ask for clarification or take an alternative.|The model directly executes tools~An agent loop never needs limits~Generating a final message proves task completion
ReAct and observation|ReAct interleaves reasoning-oriented decisions with actions and observations to adapt to external information.|The runtime alternates model decisions and tool results; useful traces capture actions, inputs, outcomes and state transitions.|Verbose reasoning text is not a reliable explanation of actual internal computation and can expose sensitive data.|A planner assumes a tool succeeded even though it returned an error. What would you enforce?|Use typed observations with status fields, require outcome checks before dependent actions, and trace decisions without relying on private chain-of-thought.|Observations can be omitted safely~Reasoning text proves internal causality~Tool errors are successful actions
Planning and task decomposition|Planning breaks a goal into manageable steps with dependencies and success criteria.|Create an initial plan, execute verifiable steps, and revise when observations invalidate assumptions.|Overplanning increases latency; rigid plans can fail when the environment changes.|A research agent follows a plan built on a nonexistent API. How should the plan evolve?|Verify prerequisites early, represent dependencies explicitly, replan from observed failures, and preserve successful work.|Plans are always correct once generated~Every task needs a long plan~Replanning requires repeating completed work
State and short-term memory|Agent state records task facts, messages, tool outcomes and control information across steps.|Keep canonical typed fields for objectives and verified facts; derive bounded model context from state rather than treating chat history as the database.|Summaries can lose constraints, and unverified model statements must not become trusted facts.|A summary drops a spending limit before a purchase request. What architecture avoids this?|Store authorization and budget as typed persisted fields, inject only needed context, and validate every proposed purchase against state.|A conversation transcript is sufficient authorization~Summaries preserve every fact~Model-written facts are automatically verified
Long-term memory|Long-term memory persists selected facts or experiences across sessions for later retrieval.|Capture consented durable records with identity, provenance, expiry and correction workflows; retrieve only relevant authorized memories.|Memory can become stale or leak data across users; indiscriminate retention is risky.|An assistant uses another customer's remembered preferences. What boundaries failed?|Namespace memory by identity, enforce access on retrieval, audit updates, and provide deletion and expiry mechanisms.|Memory retrieval needs no access controls~All observations should be retained forever~Persisted memory never becomes stale
Context engineering|Context engineering selects and structures the information a model receives at each decision point.|Prioritize instructions, verified state, relevant evidence and compact tool results under an explicit token budget.|More available information is not always better; context selection becomes a controllable subsystem.|A model spends its whole budget reading huge tool logs. How would you improve the loop?|Return structured summaries and relevant excerpts with retrievable raw references, preserve failures and constraints, and measure information loss.|Every raw log must enter context~Context engineering is only prompt wording~Compression cannot alter reasoning outcomes
Human-in-the-loop|Human review pauses execution at meaningful decision boundaries to approve, reject or modify proposed operations.|Persist the exact pending request, show its effects, bind approval to its parameters, and revalidate authorization on resume.|A generic approval can become invalid if the request changes or the environment drifts.|A user approves a small transfer, then the agent changes the amount. What must happen?|Invalidate the approval, require review of the changed operation, and record a single-use receipt for the exact request.|Approval covers all future operations~Changing parameters preserves consent~A model can approve its own sensitive actions
Multi-agent coordination|Multi-agent systems partition responsibilities across cooperating model-driven actors with shared or exchanged state.|A supervisor assigns bounded tasks; workers return evidence-backed results; coordination reconciles conflicts and tracks dependencies.|Delegation adds communication overhead and correlated errors; multiple agents do not imply independent verification.|Three agents agree on the same false source. Why is consensus insufficient?|Check shared evidence and model bias, introduce independent verification or deterministic checks, and compare against a simpler single-agent baseline.|Agent agreement proves truth~Delegation eliminates coordination cost~More agents always increase success
# durable
Persistent state and checkpointing|A checkpoint stores sufficient execution state to continue a run from a known boundary after interruption.|Persist task identity, current state, completed steps and pending work transactionally; reload the latest committed checkpoint on recovery.|A checkpoint does not by itself make external side effects atomic.|The process crashes after a payment succeeds but before state is saved. What should recovery do?|Reconcile with the external service using an idempotency key or operation ID before retrying; never infer payment failure from a missing checkpoint.|A checkpoint makes every side effect exactly once~Chat history is always enough to resume~Missing local state proves an external operation failed
Durable execution|Durable execution preserves workflow progress across process failures and replays or resumes work under explicit semantics.|Separate deterministic orchestration from recorded nondeterministic operations; persist results and checkpoints around durable boundaries.|Replayed code must not blindly repeat side effects or time-dependent decisions.|A resumed agent calls the same external API twice. How would you structure durable boundaries?|Record the action result and stable operation ID, isolate side effects, make retries idempotent, and test crashes at every boundary.|Durability means the process never crashes~All arbitrary code is replay-safe~Every resumed run starts from the beginning
Task queues and leases|A task queue decouples submission from execution and allows bounded workers to process durable jobs.|Workers claim jobs with leases, heartbeat during execution, acknowledge completion, and retry abandoned work.|Common queues offer at-least-once delivery, so duplicate work is expected and must be safe.|A worker dies while holding a job. How does another worker safely recover it?|Expire the lease, reclaim the job, reconcile completed effects, and prevent stale workers from committing using fencing or version checks.|Queues guarantee no duplicate delivery~Acknowledging before work is always safe~Expired workers cannot finish later
Retries and exponential backoff|A retry repeats a failed operation, typically after a delay; exponential backoff and jitter reduce synchronized pressure.|Classify transient versus permanent failures, cap attempts and elapsed time, respect retry hints, and reuse idempotency keys.|Retrying unauthorized or invalid requests wastes resources; retry storms can worsen outages.|A downstream service starts timing out and agent traffic triples. What policy should change?|Limit attempts, add jitter and a circuit breaker, bound concurrent work, and avoid nested retry multiplication.|Every error is transient~Unlimited retries improve reliability~Fixed synchronized retries prevent overload
Idempotency|An idempotent operation has the same intended effect when repeated as when performed once.|Associate requests with stable operation keys, persist outcome records, and return the prior outcome for duplicate requests.|Key scope and retention matter; different payloads must not silently share the same key.|A retried email tool sends two messages. How would you prevent duplicates?|Use an operation ledger and stable request identity; prefer provider deduplication, reconcile uncertain outcomes, and reject key reuse with different payloads.|Every HTTP POST is idempotent~New retry keys prevent duplicates~Idempotency means no logs change
Retry versus resume|Retry repeats a specific operation; resume continues a saved workflow from a recorded execution boundary.|Use checkpoint state to identify outstanding work and apply operation-level retry policies only where needed.|Resumption can still retry an uncertain step, so reconciliation and idempotency remain necessary.|A two-hour run fails at the final step. How do you avoid redoing two hours of work?|Persist completed-step outputs, load the last checkpoint, and retry only the remaining action after checking any uncertain side effect.|Resume always restarts the entire workflow~Retries replace checkpoints~Checkpoints remove all operation failures
Cancellation and interruptions|Cancellation expresses a request to stop work; interruption pauses execution for external input or control.|Persist cancellation state, check at cooperative boundaries, stop scheduling work, and explicitly handle already-issued operations.|Some external actions cannot be undone; terminating a process alone may leave work running elsewhere.|A user cancels while an upload is underway. What completion semantics would you define?|Stop new actions, attempt provider cancellation, report unavoidable committed effects, and checkpoint a final cancelled status.|Cancellation rolls back every effect~Killing a worker stops remote work~Paused and cancelled states are equivalent
Execution budgets and loop prevention|Budgets bound steps, wall time, token usage and resource cost so an agent cannot run indefinitely.|Maintain counters in durable state, enforce hard limits in the runtime, and detect repeated actions without progress.|A model's promise to stop is insufficient; budgets need application enforcement.|An agent stays under the step cap but makes extremely expensive calls. What else should be bounded?|Track per-tool cost, tokens, elapsed time and concurrency; reserve capacity before execution and stop or request review before exceeding limits.|Step count alone bounds cost~Models enforce billing limits automatically~Budget counters can reset on every retry
Execution observability|Observability links state transitions, model calls and tools into inspectable trajectories for debugging and audit.|Assign run and step IDs, record durations and outcomes, redact sensitive values, and correlate checkpoints with external operation IDs.|Full raw logs can leak personal data and create storage costs; aggregate metrics cannot explain every failure.|A run reports success but a downstream record was never created. What evidence do you need?|Trace the expected state transition, tool request, provider acknowledgment and verification result; define success by observed effects.|A final model message proves success~Aggregate latency explains every failure~All prompts should be logged without redaction
# tools
Function calling lifecycle|Function calling lets a model propose a named tool and structured arguments; the application executes the operation.|The runtime exposes schemas, receives requests, validates and authorizes inputs, calls handlers, and returns tool results for interpretation.|A proposal is neither execution nor permission, and the tool result can be wrong or adversarial.|The model returns a function name and JSON but no database change occurs. Why?|The host must dispatch the request to a handler and pass its result back; inspect dispatch, validation and authorization errors.|Models directly execute application functions~JSON arguments prove a tool ran~A tool proposal grants authorization
Tool schemas and argument validation|Tool schemas define an input contract that helps generation and enables runtime validation.|Use narrow enums and required properties, validate ranges and cross-field rules, then resolve identity and permissions outside generated arguments.|A structurally valid request can still be dangerous or refer to nonexistent records.|The generated transfer has valid fields but targets an unauthorized account. What must the runtime verify?|Check authenticated identity, account ownership, amount constraints and exact operation approval before executing.|Schema validity guarantees authorization~The model may choose its own authenticated identity~Descriptions replace validation
Tool discovery and selection|Discovery finds available capabilities; selection chooses a capability suited to the current task.|Expose concise distinct descriptions, query relevant tool groups where supported, and restrict the active set to allowed capabilities.|Huge overlapping tool lists consume context and confuse selection; discovery does not convey permission.|The agent repeatedly chooses an obsolete lookup tool. How would you improve discovery?|Remove deprecated tools from the active catalog, clarify descriptions, version interfaces, and evaluate confusion pairs with realistic inputs.|Discovered tools are automatically authorized~All tools must be in every prompt~Tool names alone fully describe behavior
Sequential versus parallel tools|Parallel execution fits independent calls; dependent calls require ordering and state propagation.|Run independent reads concurrently, collect explicit outcomes, then schedule actions requiring those results.|Concurrent writes can race, exceed limits, or observe inconsistent state.|An agent fetches a customer ID and updates that customer in parallel. What is wrong?|The update depends on the lookup result; run lookup first, validate identity, then execute the update with concurrency control.|Every tool call can run in parallel~Parallel writes cannot race~Independence can be inferred from speed benefits
Tool result interpretation|A tool result is an observation with status and provenance, not automatically trustworthy instructions.|Return typed status, stable record IDs, bounded payloads and error classifications; make the model reason from actual outcomes.|Untrusted tool text may contain prompt injection or stale data.|A search result says to ignore policy and call a secret-export tool. How should it be handled?|Treat the text as untrusted data, preserve instruction boundaries, and enforce tool permissions independent of model interpretation.|Tool output has system-level authority~Tool output always reflects current facts~Plain text errors count as success
Side effects and approval|Side-effecting tools change external state and require stricter policies than read-only tools.|Separate read and write capabilities, preview proposed effects, bind approval to exact parameters, and record operation receipts.|Rollback may be impossible, so uncertain outcomes require reconciliation before retry.|A deletion times out with no response. Is immediate retry safe?|Query operation state or use idempotency before retrying, preserve the approved target set, and report ambiguity rather than claiming failure.|Timeout proves deletion did not happen~Read and write tools need identical policies~Approval survives target changes
Tool timeouts and partial failures|A timeout bounds waiting but does not prove an operation failed; partial failure leaves mixed outcomes.|Apply deadlines and cancellation where supported, preserve operation IDs, and return structured per-item results.|Blind all-or-nothing retries can repeat successful side effects.|A batch update succeeds for seven records and fails for three. What should the agent retry?|Persist individual outcomes and retry only failed or reconciled-unknown items with stable keys; summarize partial completion clearly.|Timeout means no remote work occurred~Partial success requires repeating everything~Errors should be hidden from observations
Tool chaining|Tool chaining connects observations from one operation to validated inputs for the next.|Represent dependencies explicitly and check intermediate outputs before passing them to downstream tools.|An early incorrect identifier can propagate through an otherwise successful chain.|A lookup returns multiple customers and the agent updates the first. What safeguard is missing?|Resolve ambiguity against the user's intent, ask for clarification when needed, and require unique verified identity before writes.|First search result is always the intended target~Successful downstream calls validate earlier assumptions~Chains need no intermediate checks
Tool evaluation|Tool evaluation measures selection, arguments, permissions, outcomes and whole-task success separately.|Use labeled expected actions, schema checks, sandboxed execution and trajectory review; allow valid alternative plans.|Exact action-string matching can reject equivalent solutions while final-answer scoring misses unsafe actions.|An agent gives the correct answer after an unauthorized data read. Did it pass?|It may pass answer accuracy but fails policy adherence; score safety and tool behavior as separate release gates.|Correct final answers excuse unsafe actions~Only tool names matter~One exact trace covers all valid solutions

MCP architecture|MCP standardizes exchange of context and capabilities between hosts, clients and servers.|A host manages user interaction and permissions, clients maintain server connections, and servers expose tools, resources and prompts.|MCP standardizes an interface; it does not guarantee server quality, permissions or model reasoning.|A team claims connecting MCP automatically makes every tool safe. What responsibilities remain?|The host must manage trust, authorization and user consent; servers and tools still need validation, isolation and safe execution.|MCP is itself a language model~Servers automatically authorize every user~The protocol eliminates tool risk
MCP tools resources and prompts|MCP tools expose executable operations, resources expose context data, and prompts expose reusable interaction templates.|Clients discover available primitives and request calls or content through the protocol; the host decides how to present and use them.|A resource may contain untrusted text, and a prompt template cannot override host policy.|A file-reading capability and a reusable review template need exposing. Which primitives fit?|Use resources for available context or tools for parameterized operations, and prompts for reusable messages; preserve host-controlled permissions.|Resources are executable model weights~Prompts grant authorization~Tools are just static documentation
MCP transports|MCP transports carry protocol messages; local stdio and remote Streamable HTTP serve different connection needs.|A host can launch a local subprocess over stdin/stdout or connect to an HTTP server with protocol-compatible messaging.|Transport choice affects deployment and authentication, not semantic safety of returned content.|A local stdio server prints debug logs to stdout and breaks communication. Why?|Stdout carries protocol messages, so send diagnostics to stderr and validate framing; keep startup and shutdown handling explicit.|Stdio uses an HTTP endpoint~Logging arbitrary text to stdout is always safe~Transport selection guarantees trust
MCP authorization and security|MCP deployments must bind access to intended resources and validate authorization according to the selected transport and specification.|For remote HTTP, follow the applicable authorization specification, validate tokens and audiences, and avoid confused-deputy or token-passthrough patterns.|Local process execution and remote delegated access have different threats; MCP capabilities are not implicit consent.|An MCP proxy forwards an unrelated client token to a downstream service. What could go wrong?|Audience and consent boundaries can be bypassed; use properly scoped credentials and explicit downstream authorization rather than blind passthrough.|Any bearer token works at any service~Token passthrough is always safe~Local and remote threat models are identical
MCP versus direct API integration|MCP provides a reusable capability interface; a direct API integration gives application-specific control over a service.|A host may discover and invoke MCP tools or implement purpose-built adapters to existing APIs.|MCP adds interoperability and discovery but still needs adapters, policy and version management.|One service has a stable narrow API used by a single app. Must it be wrapped in MCP?|No; choose direct integration when it is simpler, and MCP when reusable client-server capability exchange justifies the overhead.|Every API must use MCP~MCP replaces all business APIs~Direct integration cannot enforce security
MCP versus function calling|Function calling is the model-facing tool request pattern; MCP is a host-server protocol for exposing and invoking capabilities.|A host can convert discovered MCP tool schemas into model tool definitions and route model requests to the server.|Not every MCP primitive is a function call, and model tool calling can exist without MCP.|A model supports tool calls but cannot connect to an MCP server. What component is missing?|A host/client adapter must handle connection, discovery, authorization and invocation; the model does not implement that transport by itself.|Function calling and MCP are identical~A model must speak MCP directly~MCP can only expose tools
Agent Skills and progressive disclosure|An Agent Skill packages reusable instructions and optional resources; discovery can expose metadata before loading full instructions.|Read skill name and description to choose relevance, load SKILL.md upon activation, and load supporting resources only when needed.|Skill text guides behavior but is not an execution sandbox or tool permission grant.|Hundreds of skills overflow model context before any task starts. What loading strategy helps?|Index brief metadata, activate relevant skills, and defer supporting files until required; verify activation with representative tasks.|Every skill file must always enter context~Skill instructions grant OS permissions~Skills are executable MCP transports
Skills versus tools versus MCP|Skills teach a task procedure, tools perform operations, and MCP standardizes capability exchange with servers.|A skill may instruct an agent how to use tools supplied directly or through MCP; these layers compose.|Procedural instructions cannot substitute for available capabilities or application authorization.|A review skill asks to run tests but the host exposes no execution tool. Can the skill run them?|No; the host needs an authorized execution capability. The skill provides guidance, not the underlying operation.|Skills create new runtime permissions~MCP is a replacement for procedural instructions~Tools and skills are mutually exclusive
Skill activation and trust|Skill activation selects reusable task instructions while retaining higher-priority policy and host-controlled execution.|Match metadata to intent, inspect instructions and referenced files, track provenance, and evaluate the skill on representative tasks.|A malicious skill can recommend unsafe behavior; portable files do not guarantee uniform host discovery or sandboxing.|A downloaded skill asks to export secrets as a setup step. What should happen?|Reject the unsafe step, inspect provenance, and enforce host permissions; do not treat skill installation as user authorization for every action.|Installing a skill approves every instruction~Portable files guarantee identical host behavior~A skill is inherently trusted system policy
# frameworks
LangChain versus LangGraph|LangChain provides model and application integrations and agent abstractions; LangGraph provides lower-level stateful graph orchestration.|Use high-level components for common patterns or explicit graphs for custom control flow, persistence and interruptions.|Frameworks reduce boilerplate but add dependencies and abstractions; neither removes the need for evaluation.|A team needs custom approvals and crash recovery beyond a simple loop. Which abstraction fits?|Use graph state, checkpointing and explicit interrupt boundaries where useful; compare complexity with a small custom orchestrator.|LangGraph is only a vector database~LangChain and LangGraph cannot work together~Framework adoption guarantees reliability
Graph nodes and edges|Nodes compute state updates; edges determine subsequent control flow through an orchestration graph.|Connect processing nodes with fixed or conditional edges, define entry and termination, and trace each transition.|Graph structure clarifies execution but a badly chosen transition can still loop indefinitely.|A graph alternates forever between planner and search nodes. What should you inspect?|Check the conditional routing predicate, progress state and stop conditions; enforce iteration and elapsed-time limits outside model suggestions.|Graph edges are embedding similarities~Graphs cannot contain cycles~Every node must call an LLM
Graph state and reducers|Graph state is shared execution data; reducers define how multiple updates combine for a state field.|Use overwrite semantics for canonical values and append or merge semantics where histories or parallel outputs require accumulation.|Blind append can duplicate messages during replay; conflicting parallel updates need explicit resolution.|Two branches update the same list and one output disappears. What is likely missing?|A suitable reducer or merge policy; define collision semantics and test concurrent updates with stable message identities.|All state fields always append~Parallel updates need no merge rules~Reducers are model training operations
Checkpoint persistence in LangGraph|A checkpointer saves graph state by execution thread so later invocations can inspect or resume it.|Configure a durable backend for cross-process persistence and identify runs consistently; in-memory saving is only process-local.|Persisting state does not make arbitrary node side effects transactional.|A graph uses an in-memory saver and loses history after restart. What should change?|Use a persistent checkpointer, preserve thread IDs, and verify restart behavior alongside tool idempotency.|In-memory checkpoints survive process restarts~Changing thread IDs resumes the same state~Checkpointing makes external writes atomic
Interrupts and human review|An interrupt suspends graph execution for external input and continuation from persisted state.|Place approval boundaries before sensitive effects, surface the pending operation, and resume with explicit human input.|Execution before an interrupt may be replayed depending on the runtime, so earlier side effects need careful handling.|A node emails a user before raising an approval interrupt and duplicates mail on resume. Why?|Place side effects after approval or isolate them in replay-safe operations with stable IDs; test the actual resume semantics.|Interrupts automatically roll back actions~All code before an interrupt runs only once~Human input can be omitted on resume
Models prompts and output parsers|Application components adapt model interfaces, format input and interpret output into usable values.|Keep prompts versioned, use typed contracts, and validate parsed results before business actions.|An output parser can enforce shape without guaranteeing meaning; abstractions can hide provider differences.|An adapter update changes structured-output behavior. How do you detect regressions?|Run contract tests and representative evaluation cases, inspect raw responses, and pin dependency and prompt versions.|Parsers prove factual correctness~All model providers behave identically~Prompt changes need no testing
Retrievers and document loaders|Loaders produce document representations; retrievers select documents relevant to a query.|Preserve metadata through loading, splitting and indexing, then evaluate query-time evidence selection separately.|Framework convenience cannot compensate for corrupted parsing or missing permissions.|A loader drops tenant metadata and retrieval leaks documents. What should be tested?|Assert metadata preservation at ingestion and enforce authorization at retrieval with tenant-isolation integration tests.|Loaders automatically enforce every permission~Retrievers train the base model~Metadata never affects retrieval safety
Runnables and composition|Composable application units connect transformations, model calls and retrieval under common invocation contracts.|Declare typed inputs and outputs, compose sequential or parallel stages, and trace errors at stage boundaries.|Convenient composition can obscure control flow or multiply hidden retries.|A composed pipeline retries each layer and overloads a provider. What would you inspect?|Trace retry ownership, set a shared deadline and attempt budget, and make one layer responsible for a clear retry policy.|Composition eliminates failures~Nested retries cannot multiply traffic~Every runnable is an autonomous agent
Framework versus custom orchestration|Framework orchestration offers reusable persistence and integration primitives; custom orchestration offers direct control.|Choose based on required recovery, routing, observability and team maintenance costs; validate behavior with representative failures.|Framework abstraction overhead and upgrades are real costs, while custom durability is easy to underestimate.|A small extraction pipeline has three fixed steps and no long-running state. Is an agent framework necessary?|A straightforward pipeline may suffice; document future persistence and approval needs before taking on framework complexity.|Every AI app needs an agent framework~Custom code never has maintenance costs~Frameworks guarantee production correctness
# evaluations
Golden evaluation datasets|A golden dataset contains curated inputs, expected behavior and judgments representative of an application's tasks.|Sample real task slices, annotate ambiguity, version labels, split development and holdout sets, and track provenance.|A small convenient set can overfit prompts and miss rare high-impact failures.|A new prompt improves the tuning set but hurts unseen customer queries. What changed?|Evaluate a protected holdout, check dataset contamination and slice coverage, and avoid iterative tuning against the release set.|Training and test examples can always be identical~A single aggregate score covers every user group~Golden labels never need correction
Deterministic evaluation checks|Deterministic checks score properties that can be established by rules such as exact choice sets, schemas or numeric invariants.|Define the acceptance condition and compare outputs without an LLM; report what the check actually establishes.|Keyword presence does not determine semantic correctness of an open-ended explanation.|An answer says checkpoints are unnecessary but contains the word checkpoint and receives full credit. What is wrong?|Keyword matching confuses mention with understanding; use a rubric with human self-assessment or a calibrated semantic judge.|Mentioning a word proves understanding~Schema checks measure all semantics~Deterministic evaluation requires an API
LLM-as-a-judge|A model judge scores outputs against criteria or comparisons rather than treating fluent text as proof of quality.|Use explicit rubrics, structured judgments, repeated or blinded comparisons and calibration against human labels.|Judges can have position bias, verbosity bias, correlated errors and prompt-injection vulnerabilities.|A judge consistently prefers longer wrong answers. How would you calibrate it?|Include concise correct and verbose incorrect counterexamples, blind order, compare against expert labels, and measure agreement by task slice.|Judges are objective ground truth~Longer answers are always better~Using the same model removes correlated errors
Pairwise evaluation|Pairwise evaluation compares two candidate outputs for the same task under stated criteria.|Randomize presentation order, allow ties, gather sufficient judgments, and aggregate win rates with uncertainty.|A win rate depends on the comparison baseline and can hide absolute quality failures.|System B beats A but both invent facts. What must the release process add?|Add absolute correctness and safety gates, report ties and slice failures, and avoid interpreting preference as factual validity.|Winning a comparison proves correctness~Pairwise evaluation has no order bias~Ties should always be forced into a winner
Rubrics and evaluator calibration|A rubric defines observable criteria and weights; calibration aligns scoring with reference judgments.|Specify performance anchors, annotate examples, compare raters, and revise ambiguous criteria before scaling evaluation.|A numerical score is only interpretable relative to its rubric and evaluator reliability.|Two interview reviewers assign 40 and 90 to the same answer. What would you improve?|Align anchors for core concepts, mechanics, examples and trade-offs; discuss disagreements and measure inter-rater consistency.|Score scales have universal meaning~Calibration is unnecessary with experts~Every criterion should reward verbosity
Agent trajectory evaluation|Trajectory evaluation examines actions and observations across a task, including safety and unnecessary work.|Score task completion, tool choice, arguments, policy compliance, recovery and efficiency with valid alternative paths.|Exact-match traces can penalize legitimate strategies, while final answers hide unsafe operations.|An agent reaches the goal through an expensive loop with unauthorized reads. How should it be scored?|Separate completion, policy and resource efficiency; fail mandatory safety gates even when the final answer is correct.|Only the final response matters~Every valid agent must use the same trace~Task success implies efficient execution
Offline versus online evaluation|Offline evaluation uses fixed or sampled cases before release; online evaluation measures behavior in deployed usage.|Use replayable tests and holdouts offline, then monitor quality, incidents and user outcomes with privacy-aware sampling online.|Production distribution changes can invalidate offline estimates; online experiments require guardrails.|Offline accuracy is high but real users abandon the assistant. What else should you measure?|Inspect task mix, latency, clarification rates, unresolved outcomes and qualitative feedback; connect success metrics to user goals.|Offline tests predict every production outcome~User clicks prove factual truth~Online monitoring replaces release tests
Synthetic datasets and contamination|Synthetic data creates evaluation cases programmatically or with models; contamination occurs when evaluation information leaks into development or training.|Generate diverse cases, review labels, deduplicate, and hold out independent real examples with tracked provenance.|A generator and judge can share blind spots; synthetic coverage is not evidence of real-world representativeness.|Every generated question looks like the prompt examples and scores perfectly. What should you change?|Broaden task and failure slices, review by humans, deduplicate near matches, and validate against independent real tasks.|Synthetic labels are always correct~Shared generator and judge guarantee independence~Duplicate cases improve coverage
Evaluation pipelines and regression gates|An evaluation pipeline runs versioned cases and compares candidate behavior against acceptance thresholds.|Store dataset, prompt, model and configuration versions; compute slice metrics and confidence intervals; gate releases on critical regressions.|A single mean can improve while important subgroups regress.|Average RAG quality improves but access-control failures appear. Should the release pass?|Fail the mandatory isolation gate, inspect per-slice changes, and treat safety thresholds separately from average usefulness.|Mean improvement excuses safety regressions~Dataset versions are irrelevant~All metrics can be collapsed into one score
# production
Latency and streaming|Latency includes queueing, retrieval, model prefill, token decoding and tools; streaming improves perceived responsiveness.|Measure time to first token and total completion separately, then optimize the stage dominating the critical path.|Streaming does not reduce total work and cannot safely expose unvalidated structured results as final actions.|Users see an immediate token but wait 40 seconds for the useful answer. What do you optimize?|Trace decode length and dependent tools, shorten unnecessary output, parallelize independent reads, and measure task completion latency.|Streaming guarantees faster total completion~First-token latency measures entire task latency~Every stage can run in parallel
Caching and semantic caching|Caching reuses prior computations; semantic caching reuses answers for sufficiently similar requests.|Key entries by relevant inputs, model and prompt versions, tenant permissions and corpus freshness; validate similarity thresholds for semantic reuse.|Near-duplicate wording can mask different dates, identities or negations.|A cache returns another tenant's answer to a similar question. What is missing?|Namespace by identity and permissions, include source versions, invalidate changes, and test sensitive near-miss queries.|Semantic similarity implies identical permissions~Caches never need invalidation~Prompts and model versions cannot affect cache correctness
Rate limits concurrency and queues|Rate limiting caps request rates; concurrency caps simultaneous work; queues buffer work within capacity.|Use bounded queues, shared limits, deadlines and backpressure; avoid dispatching more model or tool work than dependencies can handle.|Unbounded queues trade immediate overload for stale tasks and memory growth.|A traffic spike creates hours of queued requests. What controls protect usefulness?|Set queue length and age limits, reject or shed excess load, prioritize tasks and report expected delays rather than accepting everything.|Queues provide unlimited capacity~Rate and concurrency limits are identical~Old queued requests stay useful forever
Model routing and fallbacks|Routing selects a model or strategy by task requirements; fallbacks handle unavailable or unsuitable primary routes.|Use cheap models for validated simple tasks and stronger models for harder cases; preserve contracts and evaluate every route.|A fallback can change quality, schema support or policy behavior rather than being a transparent substitution.|A fallback model emits plain prose where strict JSON is required. Cost and token budgets|Cost management tracks input, output, cached and tool usage per task rather than only per model call.|Estimate worst-case loop usage, enforce runtime budgets, attribute tokens to spans, and optimize retrieval and repeated context.|Reducing model price can increase total cost if it causes more retries or steps.|A cheaper model doubles retries and tool calls. Tracing and observability|Tracing correlates requests across retrieval, models and tools; metrics summarize behavior; logs preserve selected events.|Use trace IDs and structured spans with versions, duration, outcomes and redacted attributes.|Collecting everything can leak sensitive data and hide signal in noise.|A production answer is wrong only for one customer segment. What trace fields help?|Capture authorized task slice, source versions, retrieval IDs, prompt/model versions and stage outcomes without unnecessary raw personal data.|Raw prompt logging is always harmless~Metrics alone expose every root cause~Trace IDs replace access controls
Prompt and model versioning|Versioning makes changes to instructions, model artifacts and configuration identifiable and reproducible.|Record immutable versions with evaluation results and request traces; compare candidates before rollout and retain rollback targets.|Provider or runtime updates can alter behavior even when application code is unchanged.|An unchanged application starts producing different answers after a model upgrade. What enables investigation?|Compare model and configuration versions, rerun regression cases, inspect migration differences, and roll back when critical gates fail.|Prompts are not code so need no versions~Model upgrades cannot change behavior~Temperature alone makes runs reproducible
Privacy and secrets management|Privacy and secret handling constrain what data enters prompts, logs, tools and retained storage.|Minimize data, isolate identities, redact sensitive logs, use narrowly scoped credentials and enforce retention/deletion policies.|Once data enters an external service or shared trace store, prompt instructions cannot undo exposure.|An API key appears in a tool error and is appended to model context. Reliability and incident response|Reliability measures sustained fulfillment of requirements under failures, distinct from isolated answer accuracy.|Define SLOs for task success, latency and safety; monitor dependencies, use circuit breakers, and investigate failures with versioned traces.|A highly accurate model can power an unreliable application if tools, state or infrastructure fail.|Answer accuracy is 98% but half of tasks time out.
